### RUSTSEC-2017-0002 — headers containing newline characters can split messages
- Aliases: CVE-2017-18587, GHSA-q89x-f52w-6hj2 | Published: 2017-01-23 | Modified: 2023-11-08 | Severity: None
- CVSS_V3: `CVSS:3.0/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:L/A:N`
- Affected crates.io/hyper: introduced:0.0.0-0 fixed:0.9.18 introduced:0.10.0 fixed:0.10.2

Serializing of headers to the socket did not filter the values for newline bytes (`\r` or `\n`),
which allowed for header values to split a request or response. People would not likely include
newlines in the headers in their own applications, so the way for most people to exploit this
is if an application constructs headers based on unsanitized user input.

This issue was fixed by replacing all newline characters with a space during serialization of
a header value.

References:
- https://crates.io/crates/hyper [PACKAGE]
- https://rustsec.org/advisories/RUSTSEC-2017-0002.html [ADVISORY]
- https://github.com/hyperium/hyper/wiki/Security-001 [WEB]

### RUSTSEC-2017-0001 — scalarmult() vulnerable to degenerate public keys
- Aliases: CVE-2017-1000168, GHSA-2wc6-2rcj-8v76 | Published: 2017-01-26 | Modified: 2023-11-08 | Severity: None
- CVSS_V3: `CVSS:3.0/AV:N/AC:L/PR:N/UI:R/S:U/C:H/I:N/A:N`
- Affected crates.io/sodiumoxide: introduced:0.0.0-0 fixed:0.0.14

The `scalarmult()` function included in previous versions of this crate
accepted all-zero public keys, for which the resulting Diffie-Hellman shared
secret will always be zero regardless of the private key used.

This issue was fixed by checking for this class of keys and rejecting them
if they are used.

References:
- https://crates.io/crates/sodiumoxide [PACKAGE]
- https://rustsec.org/advisories/RUSTSEC-2017-0001.html [ADVISORY]
- https://github.com/dnaq/sodiumoxide/issues/154 [REPORT]

### RUSTSEC-2017-0003 — Hostname verification skipped when custom root certs used
- Aliases: CVE-2017-18588, GHSA-jqqr-c2r2-9cvr | Published: 2017-03-15 | Modified: 2023-11-08 | Severity: None
- CVSS_V3: `CVSS:3.0/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:L/A:N`
- Affected crates.io/security-framework: introduced:0.0.0-0 fixed:0.1.12

If custom root certificates were registered with a `ClientBuilder`, the
hostname of the target server would not be validated against its presented leaf
certificate.

This issue was fixed by properly configuring the trust evaluation logic to
perform that check.

References:
- https://crates.io/crates/security-framework [PACKAGE]
- https://rustsec.org/advisories/RUSTSEC-2017-0003.html [ADVISORY]
- https://github.com/sfackler/rust-security-framework/pull/27 [WEB]

- Aliases:  | Published: 2017-04-17 | Modified: 2020-10-02 | Severity: None
- Affected crates.io/lz4-compress: introduced:0.0.0-0

### RUSTSEC-2017-0004 — Integer overflow leads to heap-based buffer overflow in encode_config_buf
- Aliases: CVE-2017-1000430, GHSA-x67x-vg9m-65c3 | Published: 2017-05-03 | Modified: 2023-11-08 | Severity: None
- CVSS_V3: `CVSS:3.0/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H`
- Affected crates.io/base64: introduced:0.0.0-0 fixed:0.5.2

Affected versions of this crate suffered from an integer overflow bug when
calculating the size of a buffer to use when encoding base64 using the
`encode_config_buf` and `encode_config` functions.  If the input string
was large, this would cause a buffer to be allocated that was too small.
Since this function writes to the buffer using unsafe code, it would
allow an attacker to write beyond the buffer, causing memory corruption
and possibly the execution of arbitrary code.

This flaw was corrected by using checked arithmetic to calculate
the size of the buffer.

References:
- https://crates.io/crates/base64 [PACKAGE]
- https://rustsec.org/advisories/RUSTSEC-2017-0004.html [ADVISORY]
- https://github.com/alicemaz/rust-base64/commit/24ead980daf11ba563e4fb2516187a56a71ad319 [WEB]

### RUSTSEC-2017-0005 — Large cookie Max-Age values can cause a denial of service
- Aliases: CVE-2017-18589, GHSA-vjrq-cg9x-rfjp | Published: 2017-05-06 | Modified: 2023-11-08 | Severity: None
- CVSS_V3: `CVSS:3.0/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H`
- Affected crates.io/cookie: introduced:0.6.0 fixed:0.6.2 introduced:0.7.0-0 fixed:0.7.6

Affected versions of this crate use the `time` crate and the method
`Duration::seconds` to parse the `Max-Age` duration cookie setting. This method
will panic if the value is greater than 2^64/1000 and less than or equal to
2^64, which can result in denial of service for a client or server.

This flaw was corrected by explicitly checking for the `Max-Age` being in this
integer range and clamping the value to the maximum duration value.

References:
- https://crates.io/crates/cookie [PACKAGE]
- https://rustsec.org/advisories/RUSTSEC-2017-0005.html [ADVISORY]
- https://github.com/alexcrichton/cookie-rs/pull/86 [WEB]

### RUSTSEC-2017-0008 — `serial` crate is unmaintained
- Aliases:  | Published: 2017-07-02 | Modified: 2024-12-04 | Severity: None
- Affected crates.io/serial: introduced:0.0.0-0

The [`serial`](https://crates.io/crates/serial) crate is no longer maintained.

Last release was on 2017-07-02.

## Possible alternatives

Consider using an alternative, for instance the blocking librarys:

- [serial2](https://crates.io/crates/serial2)
- [serialport](https://crates.io/crates/serialport)

or async alternatives:

- [mio-serial](https://crates.io/crates/mio-serial)
- [tokio-serial](https://crates.io/crates/tokio-serial)

References:
- https://crates.io/crates/serial [PACKAGE]
- https://rustsec.org/advisories/RUSTSEC-2017-0008.html [ADVISORY]
- https://github.com/dcuddeback/serial-rs/issues/71 [REPORT]

### RUSTSEC-2017-0006 — Unchecked vector pre-allocation
- Aliases: GHSA-mcrf-7hf9-f6q5 | Published: 2017-11-21 | Modified: 2023-11-08 | Severity: None
- Affected crates.io/rmpv: introduced:0.0.0-0 fixed:0.4.2

Affected versions of this crate pre-allocate memory on deserializing raw
buffers without checking whether there is sufficient data available.

This allows an attacker to do denial-of-service attacks by sending small
msgpack messages that allocate gigabytes of memory.

References:
- https://crates.io/crates/rmpv [PACKAGE]
- https://rustsec.org/advisories/RUSTSEC-2017-0006.html [ADVISORY]
- https://github.com/3Hren/msgpack-rust/issues/151 [REPORT]
