## Description (verbatim)

## Summary

`lightwalletd` can be remotely crashed through the public `GetMempoolTx` gRPC method when a backend mempool transaction disappears between `getrawmempool` and `getrawtransaction`.

`GetMempoolTx` correctly acknowledges that mempool transactions can disappear during this backend race and treats `getrawtransaction` failure as non-fatal. However, the code leaves the txid in the global `mempoolList` while omitting it from `mempoolMap`. Later in the same request, the response loop iterates over `mempoolList`, reads a missing map entry, and passes `nil` to `common.FilterTxPool`.

`FilterTxPool` immediately dereferences the nil `*CompactTx`, causing a panic. The production gRPC server path does not install a panic recovery interceptor, so the panic terminates the entire targeted `lightwalletd` process.

A local regtest PoC using real `zcashd`, a host-run `lightwalletd`, and a public gRPC `GetMempoolTx` client demonstrates that the targeted `lightwalletd` process exits with:

```text
panic: runtime error: invalid memory address or nil pointer dereference
github.com/zcash/lightwalletd/common.FilterTxPool(0x0, ...)
github.com/zcash/lightwalletd/frontend.(*lwdStreamer).GetMempoolTx(...)
```

## Finding Description

`GetMempoolTx` maintains two global structures:

```go
// Key is 32-byte txid (as a 64-character string), data is pointer to compact tx
var mempoolMap *map[string]*walletrpc.CompactTx

// Txids in big-endian hex (from the backend)
var mempoolList []string
```

During refresh, `getrawmempool` returns the list of current txids:

```go
result, rpcErr := common.RawRequest("getrawmempool", params)
...
err := json.Unmarshal(result, &mempoolList)
...
newmempoolMap := make(map[string]*walletrpc.CompactTx)
```

For each txid, `GetMempoolTx` fetches and parses the raw transaction:

```go
params := []json.RawMessage{txidJSON, json.RawMessage("0")}
result, rpcErr := common.RawRequest("getrawtransaction", params)
if rpcErr != nil {
    // Not an error; mempool transactions can disappear
    continue
}
...
newmempoolMap[txidstr] = tx.ToCompact( /* height */ 0)
```

The `continue` is the vulnerable branch. It handles a normal backend race, but it only skips insertion into `newmempoolMap`; it does not remove the txid from `mempoolList`.

After refresh, `mempoolMap` is replaced:

```go
mempoolMap = &newmempoolMap
```

The same request then iterates over `mempoolList` and assumes every returned txid has a non-nil compact transaction in `mempoolMap`:

```go
for _, txid := range MempoolFilter(mempoolList, excludeHex) {
    if ftx := common.FilterTxPool((*mempoolMap)[txid], exclude.PoolTypes); ftx != nil {
        err := resp.Send(ftx)
        if err != nil {
            return err
        }
    }
}
```

For a disappeared transaction, `(*mempoolMap)[txid]` is `nil`. `FilterTxPool` immediately dereferences that nil pointer:

```go
func FilterTxPool(tx *walletrpc.CompactTx, poolTypes []walletrpc.PoolType) *walletrpc.CompactTx {
    r := &walletrpc.CompactTx{
        Index: tx.Index,
        Txid:  tx.Txid,
        Fee:   tx.Fee,
    }
    ...
}
```

This causes a nil pointer panic. In the production server setup, the configured interceptors do not recover panics, so the panic terminates the process.

## Impact Explanation

Impact level: High.

This is a targeted remote availability issue in supporting infrastructure. It does not affect Zcash consensus, does not kill the backend `zcashd` or `zebrad`, and does not automatically propagate to other `lightwalletd` nodes. However, it does terminate the targeted `lightwalletd` process.

Practical impact:

- A public `GetMempoolTx` request can crash the targeted `lightwalletd` process.
- The gRPC client receives EOF / `Unavailable`.
- All gRPC services on that instance become unavailable.
- All wallet clients using that instance lose service until the operator restarts it.
- The attack is non-distributed: each public `lightwalletd` endpoint must be targeted individually.

The observed impact maps to a non-distributed denial of service against an individual supporting-infrastructure node.

## Likelihood Explanation

Likelihood level: Medium.

The affected method is public and unauthenticated. The attacker does not need backend RPC credentials, filesystem access, wallet keys, or operator privileges.

The exploit requires a timing condition: a txid must be returned by `getrawmempool`, and the corresponding transaction must disappear before `getrawtransaction(txid, 0)` is processed. This is not a one-packet deterministic crash against every request. However, the condition is a normal backend state transition that the code comment already acknowledges:

```go
// Not an error; mempool transactions can disappear
```

An attacker can improve reliability by:

- causing a valid transaction to enter the target backend mempool,
- using transactions likely to disappear quickly, such as short-expiry transactions or transactions around block/mempool churn,
- repeatedly polling `GetMempoolTx` around block production or mempool churn,
- setting `poolTypes` to include `TRANSPARENT`, although the nil dereference occurs before the pool-specific response can be safely built.

The localnet PoC uses a scheduling proxy only to make this race deterministic for reviewers. The proxy is not an attacker capability assumption.

## Severity Discussion

Per the ZCG Security & Vulnerability Disclosure Initiative, `lightwalletd` is Supporting Infrastructure. This report recommends High because the demonstrated outcome matches the taxonomy example:

```text
Non-distributed denial of service against an individual node or wallet.
```

The issue is not a network-wide halt or consensus failure. The affected system is the targeted `lightwalletd` instance. The High argument is that an unauthenticated remote client can cause a full process crash of public wallet-supporting infrastructure, denying service to all clients using that instance.

The main limiting factor is exploit complexity: the attacker must hit the mempool disappearance race. This is why the likelihood is Medium rather than High. The impact, once triggered, is a confirmed full-process denial of service.

## Attacker Model, Scope, and Triage Notes

Attacker model:

- The attacker does not need access to the `lightwalletd` host.
- The attacker does not need backend RPC credentials.
- The attacker does not need wallet keys, validator privileges, or admin access.
- The attacker needs access to the public `lightwalletd` gRPC endpoint.
- The attacker needs a transaction to appear in the target backend mempool and disappear during a `GetMempoolTx` refresh.

Scope fit:

- `lightwalletd` is listed under Supporting Infrastructure.
- The affected method is a public wallet-facing gRPC API.
- The issue is a targeted non-distributed DoS against one supporting-infrastructure instance.
- The PoC is isolated to local regtest and does not touch public mainnet or testnet infrastructure.

Expected pushback:

- Pushback: "The PoC uses a JSON-RPC proxy."
  - Response: The proxy is only a deterministic race scheduler for localnet validation. It forwards `getrawmempool` and `getrawtransaction` to the real `zcashd`; the final `getrawtransaction` error is a real backend `-5` after the transaction expires.

- Pushback: "This does not affect consensus or other nodes."
  - Response: Correct. This is why the report maps to non-distributed denial of service against an individual node, not a network-wide consensus issue.

- Pushback: "The attacker must hit a race."
  - Response: Correct. That affects exploit complexity and likelihood, but the race is a normal mempool condition and the demonstrated effect is a full process crash.

- Pushback: "A supervisor can restart lightwalletd."
  - Response: Restart is recovery, not prevention. The vulnerable request can crash the process again when the race is hit.

## Remediation

The response loop should not call `FilterTxPool` on a missing mempool map entry. A minimal fix is to skip nil entries:

```go
for _, txid := range MempoolFilter(mempoolList, excludeHex) {
    tx := (*mempoolMap)[txid]
    if tx == nil {
        continue
    }
    if ftx := common.FilterTxPool(tx, exclude.PoolTypes); ftx != nil {
        err := resp.Send(ftx)
        if err != nil {
            return err
        }
    }
}
```

The refresh path should also maintain the invariant that every txid used for response filtering has a corresponding non-nil map entry. When `getrawtransaction` fails for a txid returned by `getrawmempool`, either remove that txid from the response list or insert a safe empty sentinel that the response path handles explicitly.

Defense in depth: add a gRPC panic recovery interceptor so one handler bug cannot terminate the entire `lightwalletd` process.

Minimal security goal: a normal mempool disappearance race must not panic `GetMempoolTx`, and no public gRPC request should be able to terminate the entire `lightwalletd` process.
