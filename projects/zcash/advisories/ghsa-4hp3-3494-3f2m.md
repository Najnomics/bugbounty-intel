## Description (verbatim)

## Summary

`lightwalletd`'s public `GetMempoolTx` gRPC method accepts an attacker-controlled repeated `exclude_txid_suffixes` list without a count cap or aggregate-byte cap.

Each suffix is limited to 32 bytes, but the number of suffixes is not bounded at the application layer. After accepting the request, `lightwalletd` takes the `GetMempoolTx` mutex, allocates and hex-encodes a string for every suffix, and sorts the full attacker-controlled list in `MempoolFilter`. This work occurs even when the backend mempool is empty and the response contains zero transactions.

A local regtest PoC using a real `zcashd`, an unmodified `lightwalletd`, and public gRPC demonstrates that one request with 120000 suffixes increased request time from 2 ms to 1209 ms and increased transient heap allocation by about 34 MiB while returning zero mempool transactions.

## Protocol-Level Mechanism

`GetMempoolTx` lets wallets avoid receiving mempool transactions they already know by sending txid suffixes in `exclude_txid_suffixes`. Semantically, this is a client-side filter hint for the server response. It is not intended to be an expensive request body whose size dominates the mempool query itself.

The vulnerable implementation boundary is:

```text
public gRPC request -> repeated suffix list -> method mutex -> reverse/hex/sort full list -> mempool response
```

The issue is not that `zcashd` returns invalid mempool data. The PoC works with an empty mempool and returns zero transactions. The issue is that a public client can make `lightwalletd` perform CPU and heap work proportional to an unbounded repeated request field before any useful mempool result exists.

Because the work occurs under the `GetMempoolTx` mutex, an expensive request also holds the same lock used by other `GetMempoolTx` calls. This makes the endpoint vulnerable to targeted latency and resource amplification with a single request near the default gRPC inbound message-size limit, and repeated requests can maintain pressure on the target instance.

## Finding Description

An unauthenticated attacker can trigger the issue through the normal public wallet-facing gRPC API:

1. The attacker connects to `CompactTxStreamer/GetMempoolTx`.
2. The attacker sends a request containing a very large `exclude_txid_suffixes` list.
3. Each suffix is at most 32 bytes, so every individual suffix passes the only length validation.
4. `lightwalletd` acquires the `GetMempoolTx` mutex.
5. `lightwalletd` allocates `excludeHex` with one string slot per attacker-controlled suffix.
6. For every suffix, `lightwalletd` allocates a reversed byte slice and hex-encodes it to a string.
7. `MempoolFilter` sorts the full exclude list and allocates `nmatches` with one integer per suffix.
8. If the backend mempool is empty, the response still contains zero transactions, but the CPU and heap work has already been performed.

The local PoC warms the mempool cache first, then sends a control request with zero suffixes and an attack request with 120000 suffixes. This isolates the vulnerable request processing from backend mempool refresh cost.

## Impact

Impact level: Medium.

This is a targeted resource-exhaustion / latency-amplification issue against an individual `lightwalletd` instance's public mempool endpoint.

Observed localnet evidence:

```text
exclude_count=0 received=0 duration_ms=19
exclude_count=0 received=0 duration_ms=2
exclude_count=120000 received=0 duration_ms=1209
baseline_ms=2 attack_ms=1209 slowdown_x=591.00
heap_before=1572184 heap_after_baseline=3186648 heap_after_attack=37611632 heap_delta_attack=34424984 objects_before=4040 objects_after_attack=457453 objects_delta_attack=453413
```

Practical impact:

- One public unauthenticated request can increase `GetMempoolTx` latency by roughly three orders of magnitude in the tested localnet setup.
- One request can add tens of MiB of transient heap allocation while returning zero transactions.
- The expensive path runs under the method mutex, so other `GetMempoolTx` callers are serialized behind the request while the lock is held.
- The attack does not require a non-empty mempool, valid transactions, high-history addresses, reorg timing, backend RPC credentials, host access, or privileged test APIs.
- Repeated requests can degrade wallet mempool synchronization for clients using the targeted `lightwalletd` instance.

This does not affect Zcash consensus, does not compromise wallet keys, does not steal funds, and does not automatically propagate across the network. The proposed severity is Medium because the demonstrated impact is public, repeatable, and resource-amplifying, but bounded to a targeted supporting-infrastructure node and not currently shown to cause a durable crash.

## Likelihood

Likelihood level: Medium.

The reachable entry point is public and unauthenticated in normal `lightwalletd` mode. The exploit path is simple:

- no chain reorg is required,
- no mempool race is required,
- no valid transaction is required,
- no high-history transparent address is required,
- no backend RPC credentials are required,
- no privileged flags such as Darkside or Ping are required.

The main practical constraints are request size and repetition. The strongest single-request payload is near the gRPC inbound message-size limit, and sustained service degradation would require the attacker to send these large requests repeatedly. This makes likelihood Medium rather than High.

## Severity Discussion

Per the ZCG Security & Vulnerability Disclosure Initiative, `lightwalletd` is Supporting Infrastructure. This report recommends Medium because the bug allows repeated, unauthenticated resource amplification against an individual wallet-supporting infrastructure node.

The issue fits Medium better than Low because the PoC demonstrates measurable CPU/latency amplification and heap growth from one public request, even with an empty mempool and zero response transactions.

The report does not claim High because the PoC does not crash the process, does not create a durable wedge, does not affect consensus or privacy, and does not show broad network impact.

## Recommended Fix

Apply effective resource bounds and canonicalization before expensive per-entry processing and before acquiring the `GetMempoolTx` mutex.

Recommended root-cause fixes:

1. Enforce a maximum number of `exclude_txid_suffixes`.
2. Enforce an aggregate-byte cap for all suffixes in the request.
3. Return `codes.ResourceExhausted` for requests that exceed service limits.
4. Canonicalize and deduplicate suffixes before sorting.
5. Move request-list transformation outside the method mutex where possible, then hold the mutex only for shared mempool state access.
6. Canonicalize `poolTypes` to a small set or bitset as defense in depth, because it is also semantically finite but encoded as a repeated field.
7. Add per-method metrics and rate limits for large `GetMempoolTx` requests.

Example sketch:

```go
const maxExcludeSuffixes = 1024
const maxExcludeSuffixBytes = 32 * maxExcludeSuffixes

func canonicalExcludeSuffixes(req [][]byte) ([]string, error) {
    if len(req) > maxExcludeSuffixes {
        return nil, status.Error(codes.ResourceExhausted, "GetMempoolTx: too many exclude suffixes")
    }

    total := 0
    seen := make(map[string]struct{}, len(req))
    excludeHex := make([]string, 0, len(req))

    for i, suffix := range req {
        if len(suffix) > 32 {
            return nil, status.Errorf(codes.InvalidArgument, "exclude txid %d is larger than 32 bytes", i)
        }
        total += len(suffix)
        if total > maxExcludeSuffixBytes {
            return nil, status.Error(codes.ResourceExhausted, "GetMempoolTx: exclude suffixes are too large")
        }

        rev := slices.Clone(suffix)
        slices.Reverse(rev)
        h := hex.EncodeToString(rev)
        if _, ok := seen[h]; ok {
            continue
        }
        seen[h] = struct{}{}
        excludeHex = append(excludeHex, h)
    }

    return excludeHex, nil
}
```

Then call this helper before acquiring `s.mutex`:

```go
excludeHex, err := canonicalExcludeSuffixes(exclude.ExcludeTxidSuffixes)
if err != nil {
    return err
}

poolMask, err := canonicalPoolTypes(exclude.PoolTypes)
if err != nil {
    return err
}

s.mutex.Lock()
defer s.mutex.Unlock()

for _, txid := range MempoolFilter(mempoolList, excludeHex) {
    if ftx := common.FilterTxPoolWithMask((*mempoolMap)[txid], poolMask); ftx != nil {
        if err := resp.Send(ftx); err != nil {
            return err
        }
    }
}
```

The exact caps can be configuration-driven, but they should be small enough that one request cannot allocate tens of MiB or hold the method mutex for seconds.
