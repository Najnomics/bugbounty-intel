## Description (verbatim)

### Summary

Lighthouse keeps proposer slashings in the operation pool so that it can include them in block proposals. A validator remains slashable even after it has exited, up until the `withdrawable_epoch`. After that, the validator is no longer slashable. However, when selecting proposer slashings during block proposals, Lighthouse only checks that a validator is not already slashed, not that it is still slashable. As a result, Lighthouse still treats a proposer slashing for a validator as valid and includes it in block proposals, even though the slashing is no longer valid. Consequently, the block proposal fails.

### Impact

An attacker can exit one of its validators and broadcast the proposer slashing via gossip. The attacker needs to time the broadcast such that the validator has exited and reached the last slot before its `withdrawable_epoch`, which leaves only a narrow window of a few hundred milliseconds before the epoch boundary. Every Lighthouse node that receives the slashing message will miss its block proposals. Block proposals by non-Lighthouse nodes are not affected. Sustaining the attack would require the attacker to repeat with a freshly exited validator every epoch. The effect clears when the chain has a new finalized checkpoint, which is typically an epoch later under normal network conditions. Therefore, the disruption is temporary.

### Patches

The operation pool now checks if the proposer is still slashable before selecting a proposer slashing. We also added a test to prevent any regression. You may refer to this commit for the details: https://github.com/sigp/lighthouse/commit/6e36491a9bcf5b1f01aa82be0db9962893cb9dd3.
