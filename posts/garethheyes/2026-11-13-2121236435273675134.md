## Analysis

**Media note (image):** A PHP playground (`main.php`) showing `<?php echo "@@" ^ ")$";` and Output `id` - i.e. XOR of two 2-char strings yields the ASCII string "id".
**Bug class:** PHP string-based WAF/filter bypass primitive (garethheyes reshares @pad1ryoshi's trick).
**Quoted verbatim (pad1ryoshi, via garethheyes's quote chain):** "PHP allows bitwise XOR operation of strings so we can 'create' words like system, id, curl... really useful for bypassing some challs that might be blocking strings." garethheyes added: "PHP is disgusting lol. You used to be able to increment strings too many years ago."
**Root cause:** PHP's `^` on strings operates byte-wise, so any target ASCII string can be synthesized from two byte strings that contain none of the blocked characters. Function names (`system`, `exec`, `id`, `curl`) and keywords can be built at runtime from allowed bytes, defeating denylist filters that block the literal words.
**Harness takeaways:** When fuzzing PHP sinks (eval, dynamic function calls, command exec) guarded by a string denylist, add XOR-string (and the classic increment-string `$a='A';$a++` -> 'B'...) construction to the payload mutators; detect server-side PHP by probing whether XOR-composed function names execute. For defenders, denylisting function-name substrings is ineffective - gate on an allowlist / disable dangerous functions.
