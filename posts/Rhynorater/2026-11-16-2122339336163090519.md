**Why it works (inference from the screenshot text; full report not public):** the authorization server allowlisted (or loosely matched) a non-HTTP scheme, so a link the attacker controls can receive the code/token; per the triage note it "works without any app installed and the attack only takes a link".

1. For each OAuth client found (authorize endpoints with `client_id`), fuzz `redirect_uri` with alternate schemes: `android-app://<attacker-pkg>/https/attacker.tld/`, `android-app://com.victim.app/https/attacker.tld/cb`, `intent://attacker.tld#Intent;scheme=https;end`, `ios-app://`, custom app schemes registered by the target (`victim://`), `javascript:` / `data:` as controls.
2. Also try prefix/suffix variants of the registered value with the alternate scheme (`android-app://<registered-host>…`).
3. Signal: authorization server issues a 302 to the non-HTTP URI with `code=`/`access_token=` instead of an error; in a browser, Chrome resolves `android-app://pkg/https/host/path` to a web URL fallback when the app is absent — check where the code lands.
4. Combine with `response_mode=fragment|form_post` and `response_type=token` toggles.
