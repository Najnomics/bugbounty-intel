## Analysis

**Bug class:** Unauthenticated guest file-upload → RCE (magic-byte / content-type confusion + config-as-code).
**Root cause (from the post):** Upload validator only inspected the first few bytes (magic header). Attacker uploaded (1) a config file with a valid header + attacker-chosen filename telling the server to treat another file in the same folder as executable code, then (2) the payload file, then requested the path. No login on any step; server ran the file as the app user.
**Harness check:**
1. Enumerate guest/anonymous upload endpoints (avatars, attachments, import, "paste", "share as guest").
2. Probe magic-byte-only checks: send a file whose first N bytes are a benign magic (PNG/PDF/ZIP/JPEG) followed by attacker content / polyglot; also try double-extension and Content-Type mismatches.
3. Look for "config next to uploads" patterns (YAML/JSON/INI/`.htaccess`/web.config/nginx includes) that the app reloads from the same directory.
4. After upload, request the returned path and any sibling paths; assert no code execution / unexpected Content-Type.
5. Automate with a polyglot corpus + path-guessing against the upload response URL.
**Takeaway for hunting harness:** Magic-byte filters are not content parsers. Treat every guest upload that lands under a web-served or config-read path as a potential RCE primitive.

**Update 2026-11-16 (his reply in thread):** asked whether the config was overwritten — "no overwrite. dropped a new config next to it" (i.e., a *new* sibling config file in the upload folder was enough for the server to pick it up).
