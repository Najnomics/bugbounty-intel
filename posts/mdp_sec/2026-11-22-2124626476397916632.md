## Analysis

**Bug class:** Unauthenticated sensitive-file exposure (PII: ~15k signup emails) via CMS media-library enumeration — CWE-548 (directory listing) + CWE-552 (files accessible to external parties). Reported Medium, triage raised to **High** (quoted Friday post).
**How found (verbatim chain):** target ran **Sitecore**; its **SOAP API lists what is in the media folders** and an ordinary self-signed-up account could call it → folder named `testing` → a CSV (an old cleanup export whose name "literally said delete") opened at a public `/-/media/` URL with **no login**. A random `?v=` query string was appended so the **origin** answered rather than a CDN cache (proves live exposure, not a stale cached object).
**Harness / recon automation (in-scope only):**
1. Fingerprint Sitecore: `/sitecore/`, `/-/media/`, `/~/media/`, `/sitecore/shell/`, `/layouts/`, `sc_` cookies, `X-Sitecore-*` headers.
2. With a normal registered account, probe the legacy SOAP endpoints (e.g. `/sitecore/shell/WebService/Service.asmx`, `/sitecore/shell/webservice/service2.asmx` — methods like `GetChildren`/`GetItemFields` on `/sitecore/media library/...`) and the Item Web API / SSC `/sitecore/api/ssc/item/` to list media-library children. Any listing returned to a low-priv user is the bug primitive.
3. Walk folders whose names hint at non-prod or exports: `testing`, `test`, `temp`, `export`, `backup`, `old`, `delete`, `archive`; fetch each item at `/-/media/<path>.<ext>?v=<random>` **unauthenticated** and diff `Age`/`X-Cache` headers to confirm origin.
4. Flag CSV/XLSX/JSON/ZIP with email/phone regex hits → stop at minimal proof (count + 1 redacted row), report.
**Generalise:** any CMS/DAM (Sitecore, AEM `/content/dam`, Umbraco `/media`, Kentico, WordPress `/wp-content/uploads/`) where an authenticated listing API reveals paths of files that are served publicly by path.
