## Analysis

**Bug class:** IDOR / broken object-level authorization (BOLA, CWE-639) on a *secondary state-changing action* in a multi-tenant vendor portal. Severity came back Medium.
**The finding:** ticket IDs were sequential/enumerable (1m+). The list view and the ticket-detail endpoint both enforced the tenant check, but the small **"mark for follow-up"** button's endpoint did not. Sending another vendor's ticket id returned their note, the note author and their vendor id; **unmark deleted** the other tenant's note; **mark again** injected the attacker's text into the victim's own ticket view (cross-tenant read + delete + write). Normal vendor login, zero victim interaction.
**Detection signal / how to automate (in-scope, two test accounts you own):**
1. Create two tenants/vendors (A, B). As B create a ticket/object; note its id.
2. Crawl every endpoint that takes that object id — not just GET detail/list, but *side actions*: follow-up/flag/star/pin/bookmark/subscribe/watch/archive/mark-read/assign/tag/note toggles, exports, counters.
3. Replay each side-action request with A's session and B's id (Autorize/AuthMatrix style). Diff responses: any 2xx that returns B's fields (note text, author, tenant id) or changes B's state = finding.
4. Test the toggle both ways (mark → unmark → mark): unmark often deletes the joined row (cross-tenant delete), re-mark writes attacker-controlled content into the victim's view (cross-tenant write / stored content injection).
5. Prioritise: "always the little buttons" — the auth middleware is usually applied to the primary CRUD routes and forgotten on later-added micro-endpoints.
