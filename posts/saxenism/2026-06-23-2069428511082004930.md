> This question is pretty revealing, actually. It kinda validates the DEBUG/allowlist path.
> 
> So… two registrations because the SGX-only proving path uses two prover legs, SGX-Geth and SGX-Reth, each with its own trusted measurement (SGX_MRENCLAVE and SGXGETH_MRENCLAVE). 
> Per Taiko's docs the Geth leg is mandatory and Geth+Reth can prove a block without ZK, so to forge a state you need a trusted registered instance for each leg.
> 
> The sharp part is that those were specific real allowlisted measurements, not arbitrary ones. 
> If the local report check had been fail-open, any genuine SGX quote over attacker-controlled code would have registered, no need to match anything. 
> Having to land on the two known trusted MRENCLAVEs is exactly what an enforced MRENCLAVE/MRSIGNER allowlist looks like. 
> 
> So those registration txs are good evidence the allowlist was live on mainnet, which is the part people kept arguing about. 
> 
> The hole was elsewhere in the policy, and that's where DEBUG fits: take the genuine allowlisted code, run it with the debug bit set (same measurement, so it clears the code allowlist), signed by the trusted signer (clears the signer check), but now the host can read enclave memory and lift the instance key straight out. 
> 
> Taiko's own respond-to-hack PR (#21827) confirms a debug enclave's reportData key material is host-readable, which is why the fix rejects DEBUG quotes and calls it a previously exploited gap.
> 
> ----
> 
> Regarding the second part of your question:
> The age gap is most likely uneven trust-root rotation, not anything cryptographically meaningful. 
> 
> MRENCLAVE allowlists don't age out on their own, so an old Geth measurement that was never revoked is still a valid entry. The non-geth leg is recent, the Geth one is considerably older, and the attacker just matched whatever each leg currently trusted. 
> 
> ----
> 
> Short version:
> specific MRs => allowlist was live
> two MRs => two SGX proof legs
> old Geth MR => stale trusted measurement still accepted
> DEBUG not checked => a real allowlisted workload can run host-readable
> 
> Which is why we can be certain that the real story is: allowlisted workload + leaked signer + DEBUG not rejected, extract the trusted instance keys, sign both legs.
