## Analysis

**Bug class:** Incomplete-patch / remediation-bypass (same impact, different path) — web3/consensus review methodology.
**Root cause (from the post):** Accepted finding #8 (High) in the @Zcash campaign (@bluethroat_labs). Not a new bug — it came out of reviewing the REMEDIATION of an already-disclosed issue. The patch closed the exact path in the original report, but the same impact was still reachable through a path the fix did not account for. (Quotes finding #7 (Moderate): root cause was inaccurate threat modelling — relying on what actors *should* do instead of what they *could* do; doctrine "Assumptions Break Systems".)
**Detection signal / how to automate:** Treat every published patch/advisory as a hunting lead. For each fixed bug: (1) extract the impact/invariant that was violated, (2) enumerate *all* code paths that can reach that impact, (3) check the patch covers each path, not just the one in the PoC. Diff the patched function's callers and alternate entry points. Re-model the actors with "what COULD they do" (capability), not "what SHOULD they do" (policy).
**Harness takeaways:** Add a "remediation review" mode: given a CVE/GHSA/report + its fix commit, generate variant inputs that hit the same sink via a different path and re-test. Maintain a per-target invariant list so a fix to one path auto-queues the others.
