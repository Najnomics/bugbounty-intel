> "Just a .pem in a public repo" is the trigger for sure, just not the bug.
> 
> This attack class is literally the first thing discussed in the "Dumb Ways to Get Rekt w/ TEEs" section of the TEE Security Handbook from @bluethroat_labs.
> 
> -----
> 
> What actually happened:
> 
> The committed key is the MRSIGNER, a publishing identity. By itself it shouldn't be enough. A verifier that pins MRENCLAVE (the measurement of the real code) won't register a malicious enclave, because different code gives a different measurement.
> 
> This is where the popular "attacker signed their own malicious enclave and MRSIGNER matched, so it registered" explanation falls apart. A malicious binary has a different MRENCLAVE and never clears the allowlist. The leaked key buys you the signer, not the code.
> 
> So what was the actual gap? The verifier never checked the enclave's ATTRIBUTES.
> 
> DEBUG is one of those attributes, reported separately from the measurement. It does not change MRENCLAVE at all. A debug enclave also surrenders its memory protection against the host, so the operator can read and write enclave memory at will.
> 
> That opens a clean path. Take Taiko's real, allowlisted prover and build it in debug mode. The measurement is unchanged, so the code allowlist passes. Sign it with the leaked key, so the signer check passes too. Now the enclave is genuine and trusted but fully exposed, so you debug into it and pull the workload signing key straight out of memory. Do it for both provers, forge an L2 state, sign with both keys, and the verifier accepts it. The bridge releases withdrawals against state that was never real.
> 
> The hardware held the entire time. A genuine, allowlisted binary was accepted while running wide open to its host, and the policy never asked the one question that mattered: is this thing in DEBUG.
> 
> And no, this wasn't a "validity proofs would have saved us, no privileged key to leak" situation. The leaked key was load-bearing. It's what let a debug build of the real prover clear the signer allowlist. The trust didn't disappear; it just... wasn't sufficiently fleshed out.
> 
> @taikoxyz's respond-to-hack PR rejects DEBUG quotes and calls the missing check a previously exploited gap. That implies MRENCLAVE/MRSIGNER allowlist was enforced, because if it had been fail-open the attacker just registers malicious code directly and debug never enters the picture. So: allowlist on, DEBUG was the gap they walked through.
> 
> Hardware security isn't "set the bit, trust the box." It's the full attestation policy, fail-closed: measurement, signer, DEBUG, TCB status, QE identity, reportData binding, version, revocation. Missing just about any one of them carries it's own UNIQUE and SIGNIFICANT security implication.
>

**Quoted post — @1041276721759043584:**

> 🚨Taiko drained for ~$1.7M. Root cause: a private key committed to a public GitHub repo.
> 
> enclave-key.pem, the RSA key used to sign all of Taiko's SGX enclaves, sat in the public taikoxyz/raiko repo. That key is the whole trust model.
> 
> The attacker derived MrSigner from the public key, signed their own malicious enclave with the leaked key, and registered as a trusted prover. The L1 contracts trust any enclave whose MrSigner matches. It matched.
> 
> From there: forged SGX attestations on fake L2 blocks, processMessage() sets the message to RETRIABLE, retryMessage() does zero proof verification, funds leave.
> 
> No key theft. No social engineering. No SGX exploit. Just a .pem in a public repo.
> 
> Good opportunity to recall that SGX is broken. But here, nobody even had to break it. 
> 
> It's just yet another key management failure. The whole system was only ever as strong as the secrecy of one RSA key, and that secrecy depended on a human not running git add . on the wrong folder. AI greps every commit of every public repo at machine speed. Assume that is already happening.
> 
> The only real exit: a verifier that checks a succinct validity proof of the L2 state transition. It trusts no enclave, no MrSigner, no operator discipline. It checks the math. In that world this exact attack becomes cryptographically impossible rather than operationally unlikely, because there is no privileged key whose leak forges the entire system. There is just a proof.
