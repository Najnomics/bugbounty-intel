# 1-Click Account Takeover via Host Header Injection

**TL;DR:** I discovered a Host header injection in the “Forgot password” flow that lets an attacker force the application to generate password-reset links pointing at an attacker-controlled domain. A single click from a victim (user or admin) delivers the reset token to the attacker, who can then complete the reset and take over the account — and if the victim is an admin, the entire company tenant.

## What happened (short)

By tampering with the HTTP `Host` header when triggering the “forgot password” flow, I caused the application to build the reset URL using my attacker-controlled host. The app emailed (or returned) a link that contained a legitimate reset token but pointed to my server. When the victim clicked the link, the token arrived at my server and I used it to reset their password and login.

This was effectively a **one-click Account Takeover (ATO)** — bypassing filters and using Host header manipulation to exfiltrate the reset token.

## Technical details

The vulnerable flow uses the request `Host` header to construct the full password-reset URL. That header is attacker-controllable in many clients and proxy tools (Burp, curl, custom scripts). Instead of using a configured canonical domain for public links, the app trusts and echoes the `Host` header into an externally-visible URL.

## Technical details

I initially tried straightforward Host header injections (using plain `Host: attacker.com`) but the application rejected or normalized them and the attack failed. While experimenting with other variations I noticed the app accepted **subdomains** of the target (for example `sub.target.com`). That gave me an idea: if the server accepts a subdomain under an attacker-controlled domain, I could craft the Host so the remainder of the original target appears to the server as part of the URL path/query.

Concretely, by using an attacker-controlled collaborator domain as the Host and appending the target as a path-like fragment (for example `attacker.com?target.com`), the application still generated the reset link but pointed it at my attacker domain while preserving the legitimate reset token as a query parameter. The victim clicking that link would send the token to my server.

## Proof of Concept

1. Create a victim account (or use one you legitimately control).
2. Submit a forgot-password request while changing the HTTP `Host` header to an attacker-controlled domain that includes the target as a path-like suffix. Example Host header used in testing:

`Host: fl4yotnepj2yj7czkqmzxbbqbhh85ytn.oastify.com?target.com`
3\. Observe the reset link generated by the application. It points to the attacker-controlled host and contains a valid reset `token` as a query parameter. Example observed URL:

`https://fl4yotnepj2yj7czkqmzxbbqbhh85ytn.oastify.com/?.target.com/auth/reset-password?username=victim%40example.com&token=1758028965_efba0176fe1cc31615ddd7969e728a26bb843aca`
4\. When the victim clicks that link, the attacker receives the token on their server, then uses it to complete the password reset flow and log in as the victim.

## Impact

- **Account Takeover (ATO)** — attacker can set a new password and log in as the victim.
- **Company Takeover** — if the victim is an admin, attacker gains administrative control over users, settings, billing, and sensitive data.
- **Data exfiltration & service abuse** — access to internal data and operations.
- **Reputation damage & compliance risk** — especially sensitive for enterprise tenants and regulated industries.

## Why this is happening

The root cause: the application uses the incoming `Host` header to assemble publicly-accessible links. The `Host` header is untrusted user input and may be modified by attackers or by intermediate proxies. Building security-sensitive URLs from it is unsafe.

Additionally, the application failed to validate or normalize Host header values and did not enforce a canonical base URL when generating password-reset emails/links.

## Recommendations (fixes)

1. **Never** use the raw request `Host` header to generate public links. Instead, use a configured canonical hostname (application configuration) or a server-side environment variable that defines the public base URL.
2. **Validate** Host header values if they must be used: allow-list only known, expected hostnames and reject or normalize everything else.
3. **Canonicalize**: normalize and enforce a scheme + hostname from configuration (e.g., `https://accounts.example.com`) when building links.
4. **Monitoring / Alerting**: log and alert on password-reset requests that contain suspicious Host header values, or a spike of reset requests for the same account.
5. **Defense in depth**: consider sending additional notifications to account owner’s email when a reset occurs (including a link to report if they did not request it).
