Moving into API security for this one, and it’s a genuinely great teaching case because the company involved got the fix wrong not once but twice, which tells you almost everything about how commonly this exact mistake gets made. Found by Jan Masters at Pen Test Partners in January 2021, reported responsibly, and it took a journalist getting involved before Peloton actually took it seriously. His own writeup is still up, full technical detail: [Tour de Peloton: Exposed user data](https://www.pentestpartners.com/security-blog/tour-de-peloton-exposed-user-data/). Genuine respect due to him here too, not just for finding it, but for sitting through 90 days of being ignored, watching the company ship a fix that didn’t actually fix anything, and still handling the whole thing by the book instead of just dropping it publicly out of frustration.

Peloton’s bikes and app talk to Peloton’s servers through an API, the same basic arrangement behind every connected device and mobile app that exists. Masters’ actual entry point was almost disappointingly simple to even locate: he pointed a request straight at api.onepeloton.co.uk/stats/workouts/details and got back a full response, user ID, workout statistics, personal details, with no login, no token, no authentication of any kind attached to the request at all. That's worth sitting with before anything else, because it's the most basic check there is on any API endpoint you're testing, and it's the one people skip past assuming surely a company this size wouldn't leave it open: just send the request with nothing attached, and see if it actually stops you.

That first endpoint alone was bad enough, but Masters didn’t stop at confirming one open door, he went looking at what else the app’s own traffic revealed, which is really the actual methodology worth internalizing here: once you’ve found one unauthenticated endpoint on a target, immediately go check whether the same carelessness extends to every other endpoint the same app talks to, because teams rarely make this mistake exactly once. He found a user search endpoint next, api.onepeloton.com/api/user/search/, that handed back profile data for literally any query string you threw at it, and critically, it did this for users who had deliberately set their profile to private. That's the detail that actually elevates this from "an API forgot a login check" to a real privacy failure, the app had a setting telling users their information was hidden, and the backend simply never enforced it.

On top of both of those, he found a third issue, an unauthenticated GraphQL endpoint handing out similar data through a completely different query mechanism. Three separate paths into the same underlying problem, which is itself worth remembering as its own lesson, a single root cause, nobody checking who’s asking before handing over data, tends to repeat itself across every endpoint built around the same object rather than showing up just once.

Masters reported all of it in January 2021 and gave Peloton the standard 90 days most responsible disclosure programs run on. Two weeks in, Peloton quietly shipped a change and said nothing to him about it. He checked, and this is the part of the story that makes the whole case worth teaching on its own: the “fix” now required you to be logged in as a Peloton user before the endpoint would respond. Authentication had been added. Authorization had not. Any one of Peloton’s three million actual customers could still query the exact same endpoint and pull back the exact same private data belonging to any other customer, age, city, weight, workout history, the private-profile data included, completely unchanged from before. The only thing that actually changed was that the attacker now needed a free account first, which, on a platform anyone can self-register for in about thirty seconds, is barely a speed bump at all.

That gap, between “did we check that a request has some valid identity attached” and “did we check that this specific identity is allowed to see this specific person’s data,” is Broken Object Level Authorization, and it sits near the top of the OWASP API Security list for a reason: it’s an extremely natural mistake to make, because adding a login wall feels like it solved the problem, and from a quick glance at a dashboard showing “unauthenticated requests: 0,” it genuinely looks solved. The actual question an API has to answer on every single request isn’t “is someone logged in,” it’s “is this specific logged-in someone allowed to see this specific object they’re asking about,” and those are two completely different checks that have to be implemented separately, because fixing the first one tells you nothing about whether the second one exists at all.

Peloton only actually closed the real gap after Pen Test Partners, having been ignored through the entire 90-day window and past it, brought in a TechCrunch journalist to reach out directly, at which point the company suddenly had an answer and a real fix within a day. Worth sitting with that detail too as its own lesson about the human side of this work entirely separate from the technical one, responsible disclosure assumes good faith on both ends, and when a company goes quiet, the researcher’s actual leverage is patience and documentation, not immediately burning the finding in frustration.

The generalizable test worth carrying out of this one into your own API work is straightforward enough to run on almost anything: whenever you find an object-level endpoint that’s protected by a login, don’t stop there and call it secure, log in as account A, note an object ID, then switch to account B and request that exact same ID. If B gets A’s data back, authentication was never the problem that needed solving, authorization was, and it still doesn’t exist.
