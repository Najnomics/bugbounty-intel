**How a missing tenant-to-SSO binding turned a valid authentication response into cross-organization account takeover**

During an authorized security assessment of a multi-tenant application, I created an ordinary trial organization and configured it to use an identity provider under my control.

That should have given me authority over users inside my own organization and nowhere else.

Instead, I discovered that I could use my SSO configuration to authenticate as an administrator belonging to a completely different organization. I did not know the administrator’s password. I did not control their identity provider. I did not have legitimate access to their tenant. All I had to know was their **email address.**

The authentication response generated by my identity provider was valid. The application accepted it exactly as expected.

The problem was that the application accepted it for the wrong organization.

I reported the vulnerability as:

***Cross-Tenant SSO Authentication Confusion Leading to Organization Account Takeover***

This article explains how the vulnerability worked, why technically valid SSO authentication was not enough, and what developers should validate when implementing SSO in a multi-tenant application.

The application followed a common multi-tenant SaaS model.

Multiple organizations or tenants used the same application, while their users, roles, data, and configurations remained logically separated. Each tenant could contain several users with different permission levels, including administrators.

The application also allowed new users to register for a trial. A trial user received a separate tenant and administrative access to that tenant.

This meant I could legitimately:

For testing, I configured an identity provider under my control. I will refer to my organization as **Organization A** and the target organization as **Organization B**.

The security boundary should have been straightforward: control over Organization A must never provide authority over users in Organization B.

However, the application’s SSO implementation did not consistently preserve that boundary.

When discussing SSO vulnerabilities, attention naturally goes toward signature validation, assertion expiration, issuers, audiences, callback URLs, and other protocol-level controls.

Those checks are important, but multi-tenant SSO requires an additional layer of validation.

The application must establish all of the following:

A successful authentication decision should conceptually resemble:

Authenticated identity

+ expected tenant

+ tenant-owned SSO configuration

+ validated login transaction

= authorized tenant session

In the vulnerable flow, the application’s decision appeared closer to:

Valid SSO response

+ matching email address

= authenticated session

That missing tenant relationship made all the difference.

While examining the login process, I noticed that the application returned several SSO-related fields during authentication discovery.

These fields appeared to tell the client whether SSO was enabled and where the authentication process should be directed. Depending on the configuration, they could contain an authentication type, SAML-related information, or other identity-provider routing data.

I first initiated a normal login flow for a user in Organization A.

Because I controlled Organization A and its SSO configuration, the application returned values associated with my identity provider. I saved those values and continued analyzing how they influenced the next stage of authentication.

I then initiated a login attempt for an administrator belonging to Organization B.

In this flow, I intercepted the application’s response and replaced the absent or different SSO-related values with the values previously returned for Organization A.

The browser was then directed to the identity provider controlled by me.

This was the critical moment.

The application had allowed SSO configuration associated with one tenant to influence the authentication flow of a user in another tenant.

But redirecting the browser to my IdP was only part of the issue. I still needed to determine how the application would map the authenticated identity after receiving a valid response.

Inside my identity provider, I created a user whose email address matched the email address of the administrator in Organization B.

This did not give me control over the real administrator’s mailbox or password. It only meant that my IdP contained a separate identity with the same email string.

**That distinction is essential.**

An identity provider controlled by Organization A should not be able to make authoritative identity claims for Organization B merely because it returns a familiar email address.

Email addresses are identifiers. They are not, by themselves, proof that an identity provider is trusted by every organization in which that address may appear.

I proceeded with the modified login flow and authenticated through my own identity provider using the duplicate identity.

My IdP generated a legitimate authentication response. From the protocol’s perspective, the response was valid: the identity provider had genuinely authenticated a user and issued an assertion containing that user’s information.

The application accepted the response, located the matching administrator account in Organization B, and created an authenticated session for it.

I was now logged in as the administrator of another organization without knowing their password.

One of the most interesting aspects of this finding was that the attack did not necessarily require breaking the underlying SSO protocol.

I did not need to forge a signature.

I did not need to steal an assertion from the target organization.

I did not need to compromise the target’s identity provider.

I did not need the victim administrator to authenticate on my behalf.

My identity provider issued a valid response for an identity that existed inside my own authentication domain. The application’s failure occurred when it decided what that identity was allowed to access.

The application proved that my IdP had authenticated the identity. It failed to prove that my IdP was authorized to authenticate identities for Organization B.

This highlights an important difference between authentication and authorization.

*“Did this identity provider authenticate the user?” and “Is this identity provider authorized to authenticate users for this tenant?” are two separate security questions.*

Cryptographic validation can answer the first question. It cannot answer the second unless the application correctly binds the identity provider, login transaction, user, and tenant together.

The entire vulnerability can be described in one sentence:

*The application trusted a valid identity assertion without confirming that the identity provider was authorized for the tenant receiving the session.*

The compromised account held administrative privileges in the target organization.

In a multi-tenant SaaS platform, obtaining access to a tenant administrator is generally not limited to reading one user’s profile. Depending on the features available to administrators, it may expose:

The exact impact depends on the application, and security reports should distinguish between verified actions and potential consequences.

However, once an attacker can authenticate as another tenant’s administrator, the primary tenant-isolation boundary has already failed. The issue becomes an organization-level compromise rather than an isolated account-access problem.

The attacker also needed very little initial access. The ability to create a trial tenant and configure its SSO settings was enough to establish the attacker-controlled side of the trust relationship.

Because this conclusion was based on black-box testing rather than source-code review, the exact internal implementation may have differed. However, the observed behavior suggested that the application did not securely bind several important objects together:

Security objectRequired relationshipSSO configurationMust belong to the authenticating tenantLogin transactionMust be bound to the intended tenantIdentity providerMust match the tenant’s configured IdPAuthentication responseMust match the original server-side transactionReturned identityMust be resolved within the expected tenantIssued sessionMust remain within that same tenant

The primary failure was that the application did not bind the identity provider to the tenant initiating the login. Because that binding was missing, Organization A’s IdP could be inserted into Organization B’s authentication flow at all.

A secondary factor made this directly exploitable: the application resolved the returned identity by email address rather than within the tenant already attached to the transaction. As a result, an assertion issued by Organization A’s IdP was accepted and mapped to a privileged user in Organization B.

Neither the IdP-to-tenant binding nor the tenant-scoped user lookup was enforced, and that combination should never have produced a valid session.

The most important remediation is to make the tenant context immutable throughout the authentication process.

Before redirecting a user to an identity provider, the server should determine the intended tenant and retrieve that tenant’s SSO configuration from trusted server-side storage.

The browser should not be able to decide which SSO configuration applies by modifying returned fields or resubmitting configuration data.

The application should also bind the authentication transaction to:

When the authentication response returns, the server should retrieve this original context and verify that the responding identity provider is the same provider selected at the start of the flow.

The returned identity must then be resolved only within the tenant already attached to that transaction.

As defense in depth, the application should also never resolve an account by searching globally for an email address; the returned identity must be looked up only within the tenant already fixed by the transaction. But the more fundamental fix is the binding above. Even a tenant-scoped lookup fails if the wrong IdP was allowed into the flow in the first place.

A useful design rule is:

*Never let the authentication response decide which tenant receives the session. The tenant must already be fixed through trusted server-side state.*

Security logging should also detect situations where the tenant, issuer, SSO configuration, or resolved account does not match the original authentication transaction.

This finding reinforced several test cases that should be included when assessing multi-tenant authentication:

Testing only whether SSO “works” for the correct tenant is not enough. Security testing must determine whether a valid authentication flow can be transplanted into an incorrect tenant context.

The most dangerous authentication vulnerabilities are not always caused by stolen passwords, broken signatures, bypassed MFA, or compromised identity providers.

Sometimes every authentication component works exactly as designed — but the application connects those components to the wrong security context.

In this case, my identity provider correctly authenticated an identity. The application correctly received a valid response. The failure occurred when the application treated that authentication as sufficient authority over an account in another organization.

The identity was valid.

The identity provider was valid.

The resulting tenant access was not.

In multi-tenant applications, authentication cannot be evaluated independently from tenant ownership. The user, identity provider, SSO configuration, login transaction, and resulting session must all remain bound to the same trust boundary.

Identity alone is never enough.
