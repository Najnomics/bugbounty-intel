Back to API security, and this one’s worth teaching specifically because the vulnerability class is almost embarrassingly simple compared to the last two in this series. No clever token-scope confusion, no object-ID swap, just a tool that was never supposed to be reachable from outside the company at all, sitting there reachable from outside the company. Found by security researcher Ryan Stevenson in early 2018, reported to T-Mobile, pulled offline within a day, and paid $1,000. Best detailed account I’ve got a working link for is [Security Affairs’ coverage](https://securityaffairs.com/72935/data-breach/t-mobile-site-bug.html), sourced from Zack Whittaker’s original ZDNet reporting, since Stevenson didn’t publish his own technical writeup the way most researchers in this series have. Respect due to him regardless, this is exactly the kind of bug that’s trivial to weaponize into a mass data-harvesting script, and he reported it instead of doing anything with it.

T-Mobile ran a subdomain, promotool.t-mobile.com, built as an internal customer care portal, somewhere staff could look up an account's details while a customer was on the phone with support. Sitting behind that portal was an API that answered a request with full account data the moment you handed it a customer's phone number appended to the end of the URL. Name, billing address, account status, whether a bill was past due, in some cases a tax ID number, and the detail that actually made this dangerous rather than just embarrassing, a reference to the customer's account PIN, the exact PIN used as a security question when calling in to support.

Here’s the part worth actually sitting with, because it’s the single most important fact in this entire report: that tool was never supposed to need a password typed in by the end user accessing it directly from a browser, because it was never supposed to be reachable by anyone outside T-Mobile’s own internal network in the first place. The intended security model for an internal support tool like this usually isn’t “require a login,” it’s “don’t expose it to the public internet at all, put it behind a VPN or an internal network boundary, and let whatever authentication your corporate network already handles do the gatekeeping.” The moment that assumption breaks, the moment the tool somehow ends up reachable from any browser anywhere, every protection the team thought they had disappears at once, because there was never a second layer underneath the network boundary to catch the fall.

Stevenson’s actual method for finding it wasn’t exotic reverse engineering or fuzzing, by every account of how this surfaced, the subdomain itself was discoverable simply by searching for it, sitting there indexed and reachable like any other public page on the internet. That’s genuinely the entire technique worth internalizing here: subdomain enumeration isn’t just for finding more application surface to attack with clever payloads, it’s just as often how you find tools that were only ever designed with an internal audience in mind and nobody ever actually verified stayed internal. A tool’s own UI telling you it’s meant for employees, a login screen branded for staff, a dashboard clearly built for customer care reps, none of that is actual protection. The only thing that matters is whether the server enforces that assumption, and the only way to know is to just try reaching it directly and see what happens.

The detail that turns this from merely bad into genuinely dangerous is the account PIN reference sitting in that response. Most companies’ support call flows use a PIN or security question specifically as proof that the caller actually owns the account before an agent will make any changes, enable a SIM swap, update billing, read out sensitive details. If an attacker can pull that exact PIN for any phone number just by querying an open API, the PIN stops being a secret the real owner holds and becomes just another field sitting in a database anyone can read. That’s the real chain this bug enabled even though it never needed to be demonstrated explicitly, leaked account data feeding directly into social engineering a phone carrier’s own support line, the kind of path that leads straight into SIM-swap account takeovers.

Worth being honest about the part of this story that makes it a genuinely good teaching case rather than just a one-off mistake: this wasn’t T-Mobile’s first time. A nearly identical bug had been found and patched on a different T-Mobile subdomain the year before, same basic shape, an internal tool exposed without authentication, customer data readable through a simple parameter. Fixing one instance of a root cause without actually addressing why it happened in the first place, somewhere in the deployment pipeline, internal tools were ending up on the public internet without anyone double-checking, just means the next internal tool someone spins up carries the exact same risk forward. A patched endpoint isn’t a fixed process.

The generalizable habit worth carrying out of this one into your own recon is almost disappointingly simple, and that’s exactly the point, you don’t need a clever technique for this bug class, you need the discipline to actually check rather than assume. Any time subdomain enumeration on a target turns up something that sounds internal, admin, portal, tool, staff, promo, care, treat that as a lead worth chasing immediately rather than skipping past on the assumption that “internal-sounding” means “properly gated.” Hit it directly with nothing attached, no login, no token, no special headers, and see whether the server actually stops you or just assumes nobody but an employee would ever think to look.
